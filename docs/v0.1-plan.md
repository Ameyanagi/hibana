# Hibana v0.1 execution plan

This plan turns the v0.1 roadmap into independently reviewable issues. It is
the source of truth for sequencing until the first usable release. Each issue
is intended to fit in one focused pull request and must leave `pixi run check`
green.

## Release contract

Hibana v0.1 is a deterministic, reusable fuzzy matching library. It prepares a
query once, matches many in-memory text candidates, returns stable scores and
source positions, supports explicit case and scoring policy, and selects a
bounded top-K without owning filesystem, terminal, or language behavior.

The public dependency direction is:

```text
StringSlice candidates
        │
        ▼
Pattern → Matcher → MatchResult
                     │
                     ▼
               stable top-K
```

Moji may become an optional foundation when transformed-to-source mappings are
needed. Yomi, Yuragi, terminal libraries, and filesystem walkers must remain
downstream.

## API decisions

These decisions are fixed for the current scalar reference slice. Changes must
update reference fixtures and include an API rationale.

| Decision | v0.1 contract |
| --- | --- |
| Preparation | `Pattern` owns the query and its prepared scalar values. |
| Reuse | `Matcher` owns a prepared `Pattern` and may match many candidates. |
| Text unit | Matching operates on Unicode scalar values, not UTF-8 bytes. |
| Positions | Zero-based Unicode scalar indices into the candidate. |
| Ordering | Positions are strictly increasing for a non-empty match. |
| Empty query | Matches every candidate with score zero and no positions. |
| Non-match | `matched == false`, score zero, and no positions. |
| Ranking | Higher scores rank before lower scores. |
| Scalar score | 100 per match; +25 for adjacency; -1 per leading/internal gap. |
| Tie-break | Equal scores choose lexicographically earlier positions. |
| Current case | Exact and case-sensitive; no implicit normalization. |
| Ownership | Results own their positions so they outlive candidate borrows. |
| Effects | Pattern preparation and matching perform no I/O. |

`matched` remains explicit because an empty-pattern match and a non-match both
have score zero. Scalar positions avoid producing invalid UTF-8 byte offsets;
applications that need transformed-to-original ranges should use a mapping
layer instead of asking Hibana to understand languages.

`Pattern`, `Matcher`, and `MatchResult` are mutable Mojo value types. A matcher
copies its prepared pattern at construction. Pattern storage has a single
canonical scalar sequence, so reachable mutations cannot desynchronize cached
text from matching state. Underscore-prefixed fields are implementation detail,
not stable API. The documented result invariants describe values at the moment
`Matcher.match` returns; callers can subsequently mutate their result snapshot.

The current reference matcher is deliberately bounded. It rejects state tables
above 1,000,000 cells, more than 25,000,000 conservative predecessor
transitions, more than 100,000,000 conservative lexicographic tie-break steps,
or dimensions outside a conservative score magnitude of 1,000,000,000. These
checks use division before multiplication, so allocation sizes, flattened
indices, transition estimates, and scores cannot overflow first. Matching is
therefore fallible. A rejected reference workload is not a non-match.

For pattern length `P` and candidate length `C`, the reference implementation
uses `O(P*C)` memory and `O(P*C^2)` score transitions. Reconstructing
lexicographic ties can make worst-case time `O(P^2*C^2)`. The implementation is
an oracle for bounded correctness fixtures; HIB-017 owns the linear production
path.

## Milestone A — reference scalar contract

Exit criterion: the exact-scalar API is usable by one downstream prototype and
serves as an oracle for later implementations.

- [x] **HIB-001: Publish the minimal result contract.** Add `MatchResult` with
  deterministic match state, score, and owned positions. Cover empty and
  non-match states. Depends on: none.
- [x] **HIB-002: Prepare patterns once.** Add `Pattern`, scalar preparation,
  length/empty queries, and construction of `Matcher` from text or a prepared
  pattern. Depends on: HIB-001.
- [x] **HIB-003: Implement the scalar reference matcher.** Use exhaustive
  dynamic programming under the documented score and tie-break. Do not add
  SIMD or application policy. Depends on: HIB-001, HIB-002.
- [x] **HIB-004: Add the first reference fixtures and example.** Cover gapped,
  contiguous, repeated, non-match, empty, case-sensitive, Unicode scalar, and
  pattern-reuse behavior. Depends on: HIB-003.
- [ ] **HIB-005: Harden scalar invariants.** Add an independent brute-force
  oracle for bounded strings and exhaustive small-alphabet fixtures. Assert
  deterministic results, strictly increasing positions, position membership,
  and score recomputation. Depends on: HIB-003.
- [x] **HIB-006: Define resource limits.** Reject or safely handle size
  multiplication overflow, document scalar reference complexity, and add long
  pattern/candidate stress fixtures without timing assertions. Depends on:
  HIB-003.

## Milestone B — explicit policy

Exit criterion: callers can choose case and ranking policy without changing the
meaning of positions.

- [ ] **HIB-007: Add nominal case policy.** Start with `EXACT` and
  `ASCII_INSENSITIVE`; add `SMART_ASCII` only if downstream use demonstrates a
  need. Preserve positions in the original candidate. Full Unicode case folding
  requires a separate mapping design and is not implied by this issue. Depends
  on: HIB-005.
- [ ] **HIB-008: Extract a scoring scheme contract.** Make score constants and
  transition scoring an explicit nominal `ScoringScheme`; preserve the scalar
  reference results as the default scheme. Avoid dynamic dispatch in the hot
  loop unless measurement justifies it. Depends on: HIB-005.
- [ ] **HIB-009: Add path-aware boundary scoring.** Add bonuses for the start of
  a candidate and positions after documented ASCII path/word separators. This
  issue handles text only: no filesystem inspection, path existence, or OS path
  normalization. Depends on: HIB-008.
- [ ] **HIB-010: Add score conformance fixtures.** Commit tables containing
  query, candidate, policy, expected score, expected positions, and tie-break
  cases for default and path schemes. Depends on: HIB-007, HIB-009.

## Milestone C — bounded ranking

Exit criterion: applications can rank streams of candidates without sorting an
unbounded result set.

- [ ] **HIB-011: Define candidate identity and ranked output.** Use caller-owned
  integer identities initially; do not create an ecosystem-wide candidate or
  array container. Specify stable ordering as score descending, then input order
  ascending. Depends on: HIB-010.
- [ ] **HIB-012: Implement bounded top-K.** Accept an explicit positive bound,
  retain at most K matches, and return stable ranked results. Test K=1, K>N,
  zero matches, tied scores, duplicate text, and empty patterns. Depends on:
  HIB-011.
- [ ] **HIB-013: Add incremental-query preparation hooks.** Reuse candidate
  scalar preparation only if Yuragi demonstrates that the ownership and memory
  tradeoff is worthwhile. This is a measurement-gated issue, not a guaranteed
  new public type. Depends on: HIB-012, HIB-016.

## Milestone D — measurement and optimization

Exit criterion: reproducible baseline data exists and the production scalar
path improves measured workloads without changing reference semantics.

- [ ] **HIB-014: Add a benchmark harness.** Provide an opt-in `pixi run bench`
  task with warmup, measured iterations, checksums that prevent dead-code
  elimination, and machine-readable output where practical. Depends on:
  HIB-005, HIB-006.
- [ ] **HIB-015: Commit representative generated datasets.** Generate fixed-seed
  ASCII words, paths, and Unicode scalar strings at 100, 10,000, and 1,000,000
  candidates. Record provenance and checksums; do not commit restricted corpora.
  Depends on: HIB-014.
- [ ] **HIB-016: Record the scalar baseline.** Measure short/long and
  match/non-match queries, repeated patterns, top-K, and incremental query
  workloads on the documented CPU/OS/compiler matrix. Publish method and raw
  output, not superiority claims. Depends on: HIB-012, HIB-015.
- [ ] **HIB-017: Implement a linear production scalar path.** Preserve HIB-010
  fixtures and use HIB-003 as an oracle. Merge only with a demonstrated
  improvement on at least two representative datasets and no material
  regression elsewhere. Depends on: HIB-006, HIB-016.
- [ ] **HIB-018: Investigate SIMD behind the same contract.** Write a design and
  benchmark prototype; do not export backend types. SIMD may be deferred from
  v0.1 if portability or measured benefit is insufficient. Depends on: HIB-017.

## Milestone E — release readiness

Exit criterion: `0.1.0` is independently installable, documented, and proven by
one downstream consumer.

- [ ] **HIB-019: Complete API documentation.** Document every exported symbol,
  complexity class, ownership rule, position unit, case behavior, scoring
  formula, and error/precondition. Depends on: HIB-006, HIB-012, HIB-017.
- [ ] **HIB-020: Add downstream proof.** Exercise the packaged API from Yuragi
  noninteractive filtering without importing Hibana internals. Record friction
  as issues rather than expanding Hibana with application policy. Depends on:
  HIB-006, HIB-019.
- [ ] **HIB-021: Verify package artifacts.** Build the exact-compiler `.mojoc`,
  run the installed-package smoke test, and validate macOS ARM64, Linux x86-64,
  and Linux ARM64 CI. Depends on: HIB-006, HIB-019.
- [ ] **HIB-022: Release audit.** Run format, tests, precompile, package smoke,
  benchmarks, changelog review, license/provenance review, and public-export
  audit. Tag only after all required gates below pass. Depends on: HIB-006,
  HIB-020, HIB-021.

## Pull-request workflow

For every issue:

1. Start from a green main branch and name the branch after one HIB issue.
2. Add or update a failing focused test or fixture before behavioral code.
3. Implement only the issue's contract; record follow-up work as a separate
   issue rather than widening the pull request.
4. Run the smallest relevant test while iterating.
5. Run `pixi run check` before handoff.
6. For performance work, attach the exact benchmark command and before/after raw
   output; correctness fixtures remain the merge gate.
7. Require CI on all declared platforms and resolve review threads before merge.

## Required v0.1 gates

### Correctness

- All reference fixtures and bounded brute-force oracle comparisons pass.
- Scalar and optimized implementations agree on match state, score, and
  positions for the conformance corpus.
- Position sequences are valid Unicode scalar indices and strictly increasing.
- Empty query, empty candidate, repeated scalars, combining scalars, emoji,
  long gaps, ties, and non-matches have explicit tests.
- Results are deterministic across repeated runs and supported platforms.
- Oversized reference workloads raise a resource error before unchecked size,
  index, transition-estimate, or score arithmetic.

### API and architecture

- The root exports only documented user-facing values.
- No CJK, filesystem, terminal, subprocess, clock, randomness, or network logic
  appears in the runtime matching path.
- Case and scoring behavior are explicit; no locale-dependent implicit policy.
- Optimized backends remain replaceable behind the reference semantics.
- At least one Yuragi integration uses only packaged public imports.

### Performance

- Benchmark methodology records CPU, OS, Mojo version, compiler options,
  dataset checksum, warmup, iterations, and summary statistic.
- The production scalar path is compared with the reference oracle on the same
  commit and improves at least two representative measured workloads.
- Top-K memory remains bounded by documented candidate preparation plus K
  retained results; full-sort fallback is not accepted as bounded top-K.
- No absolute latency or superiority claim enters the README without repeatable
  public evidence.

### Packaging and release

- `pixi install --locked` and `pixi run check` pass from a clean clone.
- The Conda recipe builds with the pinned Mojo compiler and its installed smoke
  test imports only the package artifact.
- Required CI passes on macOS ARM64, Linux x86-64, and Linux ARM64.
- Changelog, compatibility, licenses, security policy, and generated-data
  provenance are current.
- There are no placeholders or undocumented symbols in the package root.

## Non-goals for v0.1

- Japanese readings, pinyin, Hangul decomposition, romanization, or any other
  phonetic generation.
- Unicode normalization or full Unicode case folding without an explicit source
  mapping design.
- Filesystem traversal, ignore-file parsing, path existence checks, shell
  history collection, terminal UI, previewing, or process execution.
- A general search index, persistent database, language server, regex engine,
  or application framework.
- GPU matching, mandatory SIMD, or backend-specific public API.
- A universal ecosystem candidate, string, array, allocator, or executor type.
- Performance claims based on unpublished data or incomparable toolchains.
